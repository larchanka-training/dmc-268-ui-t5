# Git-процесс: workflow

Конвенции веток и коммитов (шаблоны имён, Conventional Commits) описаны ниже кратко и являются частью workflow, а не отдельным документом.

## Workflow: начать задачу

1. Создай ветку от актуального `main`:
   ```bash
   git checkout main && git pull
   git checkout -b <type>/<краткое-описание>    # type: feat | fix | refactor | test
   ```
   Прямые коммиты в `main` запрещены.

## Workflow: закоммитить изменения

1. Просмотри изменения: `git status && git diff`.
2. Добавь адресно: `git add <файлы>` (не `git add -A` вслепую).
3. Коммит по Conventional Commits, заголовок в повелительном наклонении до ~50 символов:
   ```bash
   git commit -m "feat: добавить колонку статуса валидации в таблицу MR"
   ```
   Типы: `feat`, `fix`, `refactor`, `test`. Тело — что и почему, по необходимости.

## Workflow: открыть / обновить pull request

1. Синхронизируй с `main`: `git checkout main && git pull && git checkout - && git merge main`.
2. Прогони сборку и линтер (workflow скилла `run`) — мержить несобирающийся код нельзя.
3. Запушь: `git push -u origin <branch>`.
4. Создай PR в `main`. Инструмент — на твоё усмотрение: если доступен MCP-сервер платформы хостинга репозитория (GitLab) — используй подходящий инструмент из него; иначе CLI платформы (`glab mr create`). Не ориентируйся на конкретные имена инструментов — они могут меняться.
5. Описание PR обязательно содержит: задачу, суть изменений, какие экраны/компоненты затронуты, как проверялась сборка.
6. При новых коммитах — повтори шаги 1, 3; PR обновится автоматически.

## Критерий успеха

- Ветка названа по шаблону `<type>/<описание>`, создана от актуального `main`.
- История коммитов соответствует Conventional Commits.
- Перед PR `npm run build` проходит без ошибок и правило «одна ветка = одна задача» не нарушено.
- PR создан в `main` с описанием по шагу 5.

Если хоть один пункт не выполнен — workflow не завершён.
